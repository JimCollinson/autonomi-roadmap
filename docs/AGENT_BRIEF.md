# Agent brief — Autonomi roadmap production content

## What this repository does

This repository contains the production roadmap body content and supporting
styles consumed by the Autonomi.com Framer site. It enables roadmap updates
through GitHub pull requests, CI validation, hosted previews, and agentic
workflows, while Framer continues to own the surrounding page structure and
global site components.

This is still a pragmatic bridge, not a full site rebuild: it allows the body
content of the roadmap to be updated on the production website via GitHub,
supports rapid updates and agentic workflows, and preserves Framer global
components. The trade-offs include style coordination with Framer and the usual
runtime-fetch limitations noted below.

## Production URLs after repository transfer

After the repository is transferred to `withautonomi/autonomi-roadmap`, production
assets should be served from GitHub Pages at:

- JSON: `https://withautonomi.github.io/autonomi-roadmap/content/roadmap.json`
- CSS: `https://withautonomi.github.io/autonomi-roadmap/styles/roadmap.css`
- Manifest: `https://withautonomi.github.io/autonomi-roadmap/manifest.json`

Pull request previews for same-repository PRs should be published under:

```text
https://withautonomi.github.io/autonomi-roadmap/pr-<PR number>/
```

## Transfer and cutover rules

- Merge the withautonomi transfer cleanup PR only **after** the repository has
  been transferred to `withautonomi/autonomi-roadmap`.
- Do not switch Framer from the old `jimcollinson.github.io` URLs until the new
  `withautonomi.github.io` Pages URLs are available and verified.
- GitHub Pages URLs do not redirect automatically after a repository transfer.
- After transfer, verify Actions and Pages settings in the `withautonomi` repo,
  then verify the manifest, JSON, and CSS URLs load from `withautonomi.github.io`.
- Only after those checks should Framer component properties/code be updated to
  the withautonomi JSON and CSS URLs.

## How it works

- The repo holds the roadmap **body content** (`content/roadmap.json`, with inline
  Markdown allowed in card bodies) and the **styling** for that section
  (`styles/roadmap.css`, including fonts).
- A small, fixed Framer **code component** (`framer/RoadmapBody.tsx`) fetches the
  JSON + CSS at runtime, runs a tiny renderer (`lib/render.js`, mirrored inside
  the component) to turn the JSON into HTML, injects the CSS, and renders it
  inline in the page. It is a code component, not an HTML embed or iframe.
- `preview/standalone.html` (generated by `npm run preview`) renders the exact
  output locally for agents/humans to check work without Framer.
- Pull requests generate the same standalone preview as a workflow artifact. Same
  repository PRs also publish it to GitHub Pages under `/pr-<PR number>/` for
  human review before merge; fork PRs use artifacts/checks only.
- Merges to `main` publish the production JSON, CSS, and manifest to GitHub Pages
  for Framer to fetch from `/content/roadmap.json`, `/styles/roadmap.css`, and
  `/manifest.json`.

Edit `roadmap.json` to change content; edit `roadmap.css` to change look/layout;
merge to `main`; Framer fetches the latest after GitHub Pages publishes. See
`README.md` for the editing schema and setup.

## Content / responsibility split

- **GitHub repo owns:** the roadmap **body** — the on-page nav pills and the
  Live / Next / Sandbox sections — plus that section's CSS, fonts and responsive
  layout.
- **Framer owns:** the surrounding page structure and global site components,
  including hero/header/intro, site navigation, and footer.

Editors must understand this boundary: hero/nav/footer are **not** edited in the
repo.

## Rationale & trade-offs

- Maintaining styles in two places (repo CSS + Framer) is not ideal, but it
  enables rapid changes by team members and coding agents without
  designer/Framer round-trips.
- The alternative — copy-pasting agent-produced HTML into a Framer HTML embed —
  was tried and is painful to maintain: per-breakpoint duplication, fixed iframe
  heights, brittle responsiveness, and no review trail.
- Rendering inline as a Framer code component auto-heights, reflows with the real
  viewport, and sidesteps the fixed-height / media-query-vs-breakpoint problems
  with embeds.
- Structured JSON is rendered through fixed templates, not raw HTML. Content is
  escaped, then limited inline Markdown is applied. Do not switch to raw HTML
  rendering without a sanitizer — repo write access would otherwise equal stored
  XSS on the public page.
- Because content is fetched client-side at load, it is not in Framer's
  pre-rendered HTML: it will not be in the initial paint or indexed by search
  engines, and there can be a brief load flash. If SEO matters, a successor path
  is a GitHub Action that syncs content into Framer CMS on push.
- Production uses GitHub Pages assets published from `main` by GitHub Actions.
  Edits are not visible until the workflow passes, Pages propagates, and
  Framer/browser refresh behavior shows the new fetches.
- Pinning the component to release-managed asset URLs would make changes go live
  only when a release is cut; using current GitHub Pages production URLs
  publishes on merge.
- `lib/render.js` (preview) and the renderer block inside `RoadmapBody.tsx` are
  intentional mirrors and must be kept in sync.
- Method v0.1 is loaded via Framer's asset CDN (`framerusercontent.com`); Inter +
  IBM Plex Mono via Google Fonts. The Method URLs are external dependencies that
  could change if Framer re-uploads the font.
- Anyone with write access can change public-site copy and links. Recommend
  branch protection, required PR review, and CODEOWNERS on `content/`, `styles/`,
  `framer/`, `lib/`, and `docs/adr/`.

## Agent checklist for changes

- Start from latest `origin/main`; do not build on open branches.
- Run `npm run test:security`, `npm run validate`, `npm run preview`,
  `python3 scripts/adr-governance.py`, and `git diff --check` before committing.
- Use the PR preview URL or artifact before merging content/style changes. It is
  a public standalone roadmap body preview, not a Framer staging page.
- Do not edit historical ADRs unless adding a clearly marked maintenance note.
- Do not create a new ADR for the repository transfer cleanup.
