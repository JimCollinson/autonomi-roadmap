# Agent brief — Autonomi roadmap content shim

> Notes for the coding agent setting up this repo on GitHub. Read this, then
> formalise the decision as an ADR using ADRKit (a draft ADR is included at the
> bottom — adapt it to ADRKit's template/numbering rather than copying verbatim).

## What we're building (in one line)

A **temporary shim** that lets team members update the **body content** of the
Autonomi roadmap (autonomi.com/roadmap) using LLM coding tools via this GitHub
repo, which is then **rendered live by Framer**. It buys us a maintainable
content-editing loop in hours, without overhauling the site.

## How it works

- The repo holds the roadmap **content** (`content/roadmap.json`, with inline
  Markdown allowed in card bodies) and the **styling** for that section
  (`styles/roadmap.css`, including fonts).
- A small, fixed Framer **code component** (`framer/RoadmapBody.tsx`) fetches the
  JSON + CSS at runtime, runs a tiny renderer (`lib/render.js`, mirrored inside
  the component) to turn the JSON into HTML, injects the CSS, and renders it
  **inline in the page** (it is a code component, **not** an HTML embed / iframe).
- `preview/standalone.html` (generated by `npm run preview`) renders the exact
  output locally for agents/humans to check work without Framer.
- Pull requests generate the same standalone preview as a workflow artifact. Same
  repository PRs also publish it to GitHub Pages under `/pr-<PR number>/` for
  human review before merge; fork PRs use artifacts/checks only.

Edit `roadmap.json` to change content; edit `roadmap.css` to change look/layout;
push; Framer shows the latest. See `README.md` for the editing schema and setup.

## Content / responsibility split

- **GitHub repo owns:** the roadmap **body** — the on-page nav pills and the
  Live / Next / Sandbox sections and footer tagline — plus that section's CSS,
  fonts and responsive layout.
- **Framer owns:** the **hero header and intro** (edited natively in Framer), and
  the styling for the hero, the site navigation and the site footer.

Editors must understand this boundary: hero/nav/footer are **not** edited in the
repo.

## Rationale & trade-offs (the core decision)

- Maintaining styles in **two places** (repo CSS + Framer) is not ideal, but it
  enables rapid changes by team members and coding agents without designer/Framer
  round-trips.
- The alternative — copy-pasting agent-produced **HTML into a Framer HTML embed**
  — was tried and is painful to maintain (per-breakpoint duplication, fixed
  iframe heights, brittle responsiveness, no review trail).
- This is a **proof of concept** to get the roadmap live within hours. A later
  stage can move all CSS into Framer, or move content into Framer CMS.

## Additional decisions, trade-offs & drawbacks to capture

These came up while building it and are worth recording in the ADR:

1. **Code component, not HTML embed.** Rendering inline (code component) instead
   of an `<iframe>` HTML embed was deliberate: it auto-heights, reflows with the
   real viewport, and sidesteps the fixed-height / media-query-vs-breakpoint
   problems we hit with the embed.
2. **Structured JSON rendered through fixed templates — not raw HTML.** Content
   is escaped, then a *limited* inline Markdown (bold/italic/code/link) is
   applied. This is a security boundary: repo content **cannot inject markup or
   scripts** into the live site. Do **not** switch to rendering raw HTML from the
   repo without a sanitizer — repo write access would otherwise equal stored XSS
   on a public page.
3. **Runtime fetch → no SEO / not in static export.** Because content is fetched
   client-side at load, it is **not** in Framer's pre-rendered HTML: it won't be
   in the initial paint or indexed by search engines, and there's a brief load
   flash. Acceptable for a POC; if SEO matters, the planned successor is a
   **GitHub Action that syncs content into Framer CMS** on push (indexable).
4. **Delivery + caching = propagation delay.** Use **jsDelivr**
   (`cdn.jsdelivr.net/gh/<org>/<repo>@<ref>/…`) for proper MIME/CORS and caching;
   `raw.githubusercontent.com` works but is less steady. Note jsDelivr caches
   aggressively (hours) — edits are **not** instantly live unless you purge the
   jsDelivr cache or use a moving `@main` ref vs a pinned `@tag`. Set editor
   expectations accordingly.
5. **Release control vs instant publish.** Pinning the component to a git
   **tag/commit** (`@v1`) means edits only go live when a release is cut; using
   `@main` publishes on merge. Trade-off between "rapid" and "controlled."
6. **No baked fallback yet.** On fetch failure the component currently shows an
   error message rather than last-known-good content — a POC limitation; consider
   baking a fallback copy in.
7. **Renderer is duplicated.** `lib/render.js` (preview) and the renderer block
   inside `RoadmapBody.tsx` are intentional mirrors and must be kept in sync.
   Future single-source: have the component `import()` the renderer from jsDelivr.
8. **Font dependency.** Method v0.1 is loaded via Framer's asset CDN
   (`framerusercontent.com`); Inter + IBM Plex Mono via Google Fonts. The Method
   URLs are external dependencies that could change if Framer re-uploads the font.
9. **Governance — edits go live.** Anyone (or any agent) with write access can
   change public-site copy/links. Even with HTML-injection blocked, wording/links
   change live. Recommend branch protection, required PR review, and CODEOWNERS on
   `content/` and `styles/`.
10. **Validate before publish.** For rapid agent edits, add a JSON Schema for
    `roadmap.json` and a CI check (and/or run `npm run preview`) so a malformed
    edit can't blank the live section.

## Considerations specifically for "rapid, repeated editing" (the POC goal)

- The **caching/propagation delay (#4)** is the most likely "I edited but nothing
  changed" gotcha — document the purge/ref strategy for editors.
- A **JSON Schema + CI validation (#10)** is the highest-value safety net for
  agent edits going to a live page.
- **PR review / branch protection (#9)** keeps "live editing" from becoming "live
  accidents."
- Keep the **renderer mirror (#7)** in sync, or remove the duplication.
- Use the PR preview URL or artifact before merging content/style changes. It is
  a public standalone roadmap body preview, not a Framer staging page.

## Draft ADR (adapt into ADRKit)

**Title:** Roadmap content as a GitHub-driven shim rendered by a Framer code component

**Status:** Accepted (temporary / proof of concept)

**Date:** 2026-06-03

**Context.** The Autonomi roadmap page needs frequent content updates by team
members and coding agents. Editing directly in Framer or pasting agent-generated
HTML into a Framer HTML embed proved unmaintainable (no review trail,
per-breakpoint duplication, brittle iframe sizing). We need a maintainable,
agent-friendly editing loop live within hours, without re-platforming the site.

**Decision.** Store the roadmap **body content** (`roadmap.json`, Markdown allowed
in bodies) and its **styles** (`roadmap.css`, incl. fonts) in a GitHub repo. A
small fixed Framer **code component** fetches both at runtime and renders the body
inline via a shared renderer. Framer retains the hero header/intro and the
nav/footer and their styles. Content is rendered through fixed templates as
escaped text + limited inline Markdown (no raw HTML), so repo edits cannot inject
markup.

**Consequences.**
- (+) Team/agents edit content & section styles in GitHub with PR review; no
  Framer copy-paste; previewable locally.
- (+) Code component (not iframe) reflows and auto-heights cleanly.
- (+) Content edits cannot inject scripts/markup into the live page.
- (−) Styles live in two places (repo + Framer) during the POC.
- (−) Runtime fetch ⇒ content not in Framer's static export (no SEO / initial
  paint; load flash).
- (−) CDN caching introduces a propagation delay; needs a ref/purge strategy.
- (−) Renderer is duplicated (preview vs component) and must be kept in sync.
- (−) External dependency on Framer-hosted font URLs.

**Alternatives considered.**
- *HTML pasted into a Framer embed* — rejected: unmaintainable, brittle, no review.
- *Framer CMS, content synced from GitHub via a GitHub Action* — deferred: best
  for SEO and native styling, but more setup than the POC timeline allows. This is
  the intended successor.
- *All styling in Framer, content only in GitHub* — deferred to a later stage.

**Follow-up / exit criteria.** Treat as a stopgap. Revisit once the roadmap needs
SEO, or once we're ready to consolidate styling into Framer or migrate content to
Framer CMS via the sync action.
